01 COMPOR COMPONENTES

LangChain e LangGraph:
Construindo aplicações com LLMs

Do prompt ao controle de fluxos com estado, decisões e agentes

Por que LangChain?

O ponto de partida

Chamar uma LLM é só uma etapa. Conforme a aplicação cresce, precisamos conectar prompts, modelos, parsers, ferramentas, documentos e retrievers.

UMA CHAIN, PASSO A PASSO
INEntradaUma pergunta
→
{ }PromptDefine a instrução
→
LLMModelGera a resposta
→
[ ]ParserOrganiza a saída
→
OUTSaídaUm resultado útil
A saída de cada componente alimenta o próximo.
prompt | model | parser

O operador | compõe um pipeline.

LangChain não é obrigatório para usar uma LLM.

É uma camada de abstração e composição. Uma aplicação simples pode utilizar diretamente o SDK do provedor.

02 CONTROLAR O FLUXO

Quando o fluxo deixa de ser
apenas uma sequência

Uma chain linear conecta etapas. Mas o próximo passo pode depender do resultado anterior — e às vezes precisamos voltar.

DA CHAIN AO GRAFO

A → B → C → D: o caminho já está definido.

E se o próximo passo depender do resultado anterior?

Esse é o papel do LangGraph.

Construir aplicações com estado usando grafos. Nós controlamos quais etapas executam, como o estado muda e quando o fluxo continua.

04 OS DADOS DO FLUXO

Três conceitos. Um grafo.

Explore cada peça. Depois acompanhe o mesmo exemplo avançando pelo atendimento.

Os dados compartilhados pelo fluxo.

O state muda conforme as etapas executam. Cada node lê os dados disponíveis e pode atualizar parte deles.

  resposta: ""

Na entrada, temos a mensagem. As outras informações ainda serão preenchidas.

05 ETAPAS DE PROCESSAMENTO

Um node faz um trabalho.

Recebe o state e normalmente devolve atualizações para ele. Pode chamar uma LLM, executar uma regra ou consultar uma ferramenta.

STATEmensagem: "Quero cancelar meu plano"
categoria: ""
resposta: ""
→
NODEclassificar_cliente(state)
→
PARTIAL STATE{ categoria: "cancelamento" }
Retornar uma atualização não apaga o restante do state.

O grafo aplica os valores retornados. Neste exemplo, a categoria muda e a mensagem permanece.

06 CONECTAR AS ETAPAS

Edges definem para onde seguir.

Uma edge fixa conecta dois nodes. Uma conditional edge escolhe o próximo node a partir do estado.

CAMINHO FIXO
Node A→Node B

Depois de A, sempre B.

CAMINHO CONDICIONAL
Node A→B ou C

Depois de A, uma decisão.

07 O STATE ORIENTA A DECISÃO

Uma decisão. Quatro caminhos.

Uma conditional edge utiliza uma função para decidir qual será o próximo node. No nosso atendimento, a função lê a categoria.

def escolher_rota(state):
    return state["categoria"]

O valor retornado é mapeado para o node de destino.

classificar
↓
escolher_rota(state)
↓
state["categoria"] = "tecnico"O próximo node será: Técnico.
08 PROMPTS DENTRO DOS NODES

Reduzir ambiguidade.
Melhorar a decisão.

O node de classificação precisa de uma instrução clara para devolver uma categoria que o grafo consiga usar.

PROMPT VAGO
“Classifique essa mensagem.”

Classificar como o quê?

Sem categorias ou formato definidos, a resposta pode não servir à função de roteamento.

UMA SAÍDA POSSÍVEL

“O cliente parece insatisfeito com o serviço.”

PROMPT ESTRUTURADO
PAPEL

Você classifica solicitações de clientes.

CONTEXTO

Atendimento de uma empresa de telefonia.

TAREFA

Classifique a mensagem recebida.

CATEGORIAS E REGRAS

tecnico · financeiro · cancelamento · comercial
Escolha apenas uma categoria.

FORMATO

Retorne somente o nome da categoria.

EXEMPLO

“Minha fatura veio errada.” → financeiro

Mensagem: “Quero cancelar meu plano.”
VAGO · SAÍDA POSSÍVEL

“Pedido de encerramento do serviço.”

ESTRUTURADO · SAÍDA ESPERADAcancelamento

Exemplos ilustrativos. Um prompt claro reduz ambiguidade; validação da saída ainda é necessária.

Prompt engineering não é escrever textos gigantes. É reduzir ambiguidade.

09 MODELOS COMO INFRAESTRUTURA

E qual modelo vamos usar?

O provider dá acesso ao modelo. LangChain e LangGraph organizam como ele participa da aplicação.

Aplicação→LangChain / LangGraph→Provider→Model

OpenRouter API unificada

Acesso a modelos de diferentes empresas por uma API. Há opções gratuitas sujeitas a limites, além de modelos com preços diferentes.

Catálogo do OpenRouter

Groq Inferência

Provider de inferência com foco em execução rápida. Disponibiliza diferentes modelos, com limites e capacidades próprios.

Catálogo da Groq
Características para escolher um modelo
TipoEm geralQuando considerar
Modelo pequenoMenor custo e maior velocidadeTarefas simples e bem delimitadas
Modelo maiorMaior capacidade; normalmente maior custo e consumoTarefas mais exigentes
Reasoning modelRaciocínio mais elaborado; pode consumir mais tokensProblemas com várias etapas
MultimodalMais de uma modalidade, conforme o modeloEntradas com texto, imagem ou áudio
Preço de entradaPreço de saídaContext windowCapabilities

Consulte sempre o catálogo atual do provider. Custo, latência e qualidade variam por modelo e tarefa.

E modelos locais?

Podemos executar modelos localmente com ferramentas como Ollama. Isso depende de recursos como RAM e VRAM. Modelos quantizados exigem menos recursos, com trade-offs de qualidade e desempenho. Nesta aula utilizaremos APIs para evitar diferenças de hardware entre os alunos.
